# SEO-контент: КАСТОМС ЛИДЕР

Здесь находятся десять редакционных черновиков под коммерческие и информационно-коммерческие запросы. Файлы Markdown — исходники для публикации; сами `.md` не нужно просто выкладывать как страницы сайта.

## Рекомендуемая публикация

Публиковать материалы отдельными HTML-подстраницами на основном домене, например `https://домен.ru/articles/dostavka-stankov-iz-kitaya/`. Для этого проекта это лучше, чем один PDF или десять отдельных файлов в корне хостинга: статья получает постоянный человекочитаемый URL, собственные `title`, `description`, canonical, хлебные крошки, внутренние ссылки и место в sitemap. Не дробить каждую статью на страницы.

Сейчас лендинг собран как React SPA на Vite, а форма и страницы заявок — клиентские. Самый бережный вариант для текущего проекта — при сборке превращать эти Markdown-исходники в статические HTML-страницы вида `dist/articles/<slug>/index.html`, добавить `/articles/index.html` как оглавление, а лендинг оставить отдельным. Альтернатива — CMS с контролируемым шаблоном, если редактору нужно самостоятельно выпускать и обновлять публикации. Google умеет рендерить JavaScript, но рекомендует учитывать, что предварительная генерация HTML ускоряет страницы для людей и роботов и помогает ботам, которые JavaScript не исполняют. Markdown можно хранить отдельными файлами **в исходниках**, но публиковать в выдачу стоит готовые HTML-подстраницы, а не `.md`, PDF или десять URL в корне.

На `/articles/` сделать страницу-оглавление с карточками статей и тематическими группами. Добавить обычные HTML-ссылки `<a href>` в футере («Полезное / Статьи») и контекстные ссылки со страниц услуг, кейсов и FAQ. Каждой важной странице нужна хотя бы одна ссылка с другой индексируемой страницы. В статьях вести к релевантной услуге и форме расчёта, а не вставлять одинаковую ссылку на заявку после каждого абзаца.

Для запуска первыми опубликовать статьи 1–5: они отвечают на задачи до заявки (общий процесс, документы, бюджет, классификация, негабарит). Затем 7–10. Раз в месяц смотреть в Вебмастере и Search Console показы, запросы, клики и переходы к форме; расширять страницы по реальным вопросам потенциальных клиентов. Не задавать фиксированное число слов как SEO-норму и не плодить почти одинаковые статьи под отдельные варианты одной фразы.

У каждой страницы — один H1, уникальные title и description, короткий постоянный slug, абсолютный canonical на основной домен, хлебные крошки и дата последней фактической проверки. Добавить URL в корневой `sitemap.xml`, открыть их для обхода и отправить sitemap в Яндекс Вебмастер и Google Search Console. Для разметки можно использовать Article и BreadcrumbList только с правдивыми автором, датами и содержанием. Разметка не гарантирует расширенный сниппет.

GitHub Pages технически может отдавать статические HTML-подстраницы и Markdown как файлы, но домен сейчас не подтверждён. Для SEO и доверия лучше использовать основной фирменный домен, а GitHub Pages — как хостинг за этим доменом, если он уже настроен. Не публиковать статьи одновременно на нескольких адресах без canonical/301.

## Редакционные ограничения

- Кластеры запросов ниже — гипотезы по тематике и содержанию проекта. Частотность, сезонность, регионы и конкуренция должны быть сверены в Яндекс Вордстате и в статистике Яндекс Вебмастера / Google Search Console перед расстановкой приоритетов.
- Таможенные платежи, код ТН ВЭД, документы о соответствии, ограничения, доступность коридоров и сроки зависят от конкретного товара, условий сделки и актуальных норм. В текстах поэтому нет таблиц ставок, обещаний универсального набора документов и транзитных нормативов.
- До публикации подтвердить, что кейс и количественные показатели сайта разрешено использовать в редакционных материалах. Не выдумывать авторов, экспертов, отзывы, сертификаты, страховое покрытие и клиентов.
- Практические чек-листы — информационные, не юридическое заключение и не расчёт для конкретной декларации. Перед публикацией правовых материалов перепроверять действующую редакцию официальных актов.
